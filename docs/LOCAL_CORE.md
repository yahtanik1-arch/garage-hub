# Локальное ядро GarageHub

В этой ветке брони, права доступа, очередь, worker, бот, Mini App и админка проверяются
без аренды VPS, аккаунта Tuya и физического замка. Внешний Telegram не вызывается.
Физическое открытие остаётся этапом T22–T26 системного дизайна.

## Первый запуск

Нужны Python 3.9, PostgreSQL 17 (включая `psql`, `pg_dump`, `pg_restore`, `btree_gist`)
и PostgREST. На macOS: `brew install postgresql@17 postgrest`.
Проверены PostgreSQL 17.11, PostgREST 16.5, Python 3.9.6.
На Linux установите соответствующие пакеты/официальный бинарник PostgREST;
если PostgreSQL вне PATH, укажите `PG_BIN=/путь/к/bin`.
Docker, Supabase CLI и облачные аккаунты не требуются.

Из корня репозитория:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python -m tools.local_db up
python -m tools.local_db test
python -m tools.local_db seed
WEB_PORT=8082 python -m tools.local_db web
```

Открыть [клиента](http://127.0.0.1:8082/?dev=client#/my) или
[администратора](http://127.0.0.1:8082/?dev=admin#/admin).
У клиента есть действующая демонстрационная бронь: «Заявки» → бронь → «Открыть бокс».
После регистрации — «Проверить результат». Для повторного входа вернуться к брони
и нажать новую кнопку. Между открытиями действует пауза не менее трёх секунд.
Администратор видит «Замки», историю команд и ручное открытие с обязательной причиной;
назначение устройства доступно через «Объекты» → объект → «Настроить замок».

`web` запускает HTTP, настоящие aiogram handlers и worker вместе. Все команды помечены
как тестовые. Нельзя выдавать подтверждение имитатора за открытие физической двери.
Остановка веба — Ctrl+C. Затем `python -m tools.local_db down` останавливает только
процессы этого стенда; данные остаются в `cache/local-db/`.
Не запускайте отдельный `worker` одновременно со встроенным, кроме испытания конкуренции.

Стенд создаёт отдельный кластер PostgreSQL на `127.0.0.1:55439`, PostgREST — на `:55440`.
Кластер не запускается как системная служба и не использует существующие базы.
Серверный JWT генерируется локально, ключи/логи/данные в `cache/`, не в git.
Аутентификация самого кластера — trust на loopback: это локальный стенд для одного
доверенного пользователя, его порты нельзя публиковать в сеть.

Команды `web/test/seed/worker` передают дочернему процессу локальные настройки и
фиктивный токен Telegram. Рабочая `.env` не перезаписывается. Имитатор и `MINIAPP_DEV`
запрещены при `APP_ENV=production`. Свой PostgREST разрешён на loopback; имя `rest`
для compose-сети разрешено только при `APP_ENV=local`.

## Проверки и сценарии отказов

`python -m tools.local_db test` запускает исходные webhook, API и сценарии бота,
а также `tests/t_access.py` на настоящей PostgreSQL. Записывающие тесты защищены от
случайного запуска на внешней базе. **Прогон очищает всю выделенную базу стенда**;
после него для просмотра выполните `seed` заново. Во время тестов остановите локальный веб.
Отдельно `python tests/t_webhook.py` работает без базы и `.env`.

Проверяются пересечения интервалов и конкурентные INSERT; атомарность подтверждения,
grant и outbox с искусственным отказом; чужой, ранний и истёкший доступ; отзыв права;
повторы, два worker, сроки, таймаут и перезапуск в `dispatching`; дубликаты, старые и
неподтверждённые события; ручные права и аудит; доставка при недоступном Telegram;
readiness, оповещения, повтор миграций и настоящее восстановление резервной копии.

Для отдельного процесса worker (при остановленном `web`):

```bash
python -m tools.local_db worker
```

Имитатор `LockSimulator` поддерживает `success`, `reject`, `offline`, `timeout`,
`no_event`, `duplicate`, `old_event`. Проверки выбирают сценарий явно; timeout не
создаёт автоматический повтор. Неопределённость разрешает оператор после проверки,
с причиной в журнале. Повторная отправка не подменяет проверку результата.

Браузерная проверка `tests/t_browser.cjs` использует Playwright как необязательный
инструмент разработки. На запущенном и наполненном `:8082`:

```bash
# Playwright должен быть установлен в окружении Node.js и иметь Chromium.
node tests/t_browser.cjs
```

Она проверяет клиентское открытие, повтор клика, повторный вход, ручное открытие,
настройку замка, ошибки JavaScript и ширину мобильного экрана. Основной Python-прогон
от Playwright не зависит. Браузерные снимки сохраняются во временном каталоге ОС.

## Данные и транзакции

Новая база: выполнить `sql/000_base.sql`, `001_v2.sql`, `002_telegram_updates.sql`,
`003_access.sql` по порядку. В облачной Supabase — вручную в SQL Editor, после backup.
Применение к рабочей базе в рамках этого PR не выполняется.

Перед 003 проверить существующие пересечения:

```sql
SELECT a.id, b.id, a.garage_id
FROM bookings a JOIN bookings b ON a.garage_id = b.garage_id AND a.id < b.id
WHERE a.status IN ('pending','confirmed') AND b.status IN ('pending','confirmed')
  AND tstzrange(a.start_time,a.end_time,'[)') && tstzrange(b.start_time,b.end_time,'[)');
```

Конфликты разбираются человеком; миграция не удаляет брони ради ограничения.
003 — одна транзакция, повторный запуск допустим. Внешним ролям не выдаются права
вызова `gh_*`; только серверный `service_role`. Клиент обращается через защищённый API.
Supabase REST-вызовы не объединяются в транзакцию на стороне Python: решения, выдача/
отзыв доступа и регистрация команды выполняются PostgreSQL RPC.
Время проверяется базой, интервал `[start,end)`, соседние брони допустимы.

Публичный каталог не содержит контактов владельца или ключей доступа.
`POST /api/bookings/{id}/unlock` принимает пустой JSON и `Idempotency-Key`;
ответ 202 содержит команду, не обещание физического открытия.
Свой статус: `GET /api/lock-commands/{uuid}`. Чужая команда недоступна.
`POST /api/admin/locks/{uuid}/unlock` дополнительно требует причину.
Настройка устройства: `POST /api/admin/locks`; просмотр: `GET /api/admin/locks`.
Разрешение неизвестного результата: `POST /api/admin/lock-commands/{uuid}/resolve`
с `state=failed|device_confirmed` и причиной. Это отдельное решение, не повтор открытия.
Для ручных операций ID должен входить и в `ADMIN_IDS`, и в `MANUAL_UNLOCK_ADMIN_IDS`.
Произвольный `device_id` в клиентском запросе открытия не принимается.

## Запуск процессов и наблюдение

Worker использует RPC и ограниченный опрос с паузой до пяти секунд при пустой очереди,
при ошибках — backoff до 30 секунд. Состояние хранится в БД. LISTEN/NOTIFY-клиент не
добавлен: текущее соединение с Supabase — HTTP. Сигнал NOTIFY не заменяет таблицу.
Захват атомарный; транзакция заканчивается до внешнего вызова. Одно устройство не
получает вторую неразрешённую команду. Восстановление и heartbeat — раз в 15 секунд.

`/api/health` — процесс работает. `/api/ready` проверяет БД/миграцию и даёт 503 при отказе.
В админке показаны heartbeat, незавершённые команды, очередь уведомлений и свежесть
состояния. Просмотр ограничен 100 строками очереди и 20 командами на замок.
Задержка команды более минуты, уведомлений более двух минут и устаревшая телеметрия
создают оповещение в outbox; повтор ограничен одним сообщением каждого вида за пять минут.
`unknown` создаёт отдельное оповещение. При отказе Telegram уведомления остаются в БД.
Для обнаружения полного отказа worker/приложения нужен внешний мониторинг на этапе T24:
мертвый процесс сам отправить сигнал не может.

В `deploy/` подготовлены два systemd unit и пример nginx. Пути `/opt/garagehub`,
пользователь `garagehub`, права на `.env`, каталоги `cache/logs`, домен и сертификат
настраиваются при T24. На VPS: `APP_ENV=production`, `MINIAPP_DEV=0`,
`LOCK_PROVIDER=disabled` до реализации проверенного Tuya adapter. При Supabase
`POSTGREST_URL` пуст; при своей PostgreSQL он указывает на приватный loopback PostgREST.
Worker в этом режиме доставляет outbox и восстанавливает состояния, но не вызывает замки.
Состояние реального сервера и оставшиеся шаги запуска — в [DEPLOYMENT.md](DEPLOYMENT.md).

## Резервное копирование, восстановление и выпуск

```bash
python -m tools.local_db backup
python -m tools.local_db restore-check
```

`backup` пишет `cache/local-db/backup.dump`. `restore-check` делает снимок, создаёт
отдельную временную БД, восстанавливает `pg_restore`, проверяет схему и запрет отправки
старых команд, затем удаляет только эту временную БД. Исходный стенд сохраняется.

После восстановления production-backup **worker должен оставаться остановленным**.
Выполнить в восстановленной БД:

```sql
SELECT gh_restore_gate(ВАШ_TELEGRAM_ID, 'Восстановление из backup от ...');
```

Восстановленные queued/dispatching/cloud_accepted блокируются как `unknown`,
уже просроченные queued становятся `expired`. Снимок мог быть сделан до фактической
отправки: отсутствие dispatching в снимке не доказывает отсутствие физического действия.
Оператор сверяет журнал/устройство, разрешает неопределённость и только затем
возобновляет работу. Само восстановление никогда не должно открывать бокс.

Перед выпуском: backup, локальные проверки, миграции, затем один процесс приложения
и один worker; проверить readiness и webhook. При откате кода сохранять новую схему,
остановить отправку и сверить незавершённые команды. Автоматического удаления таблиц
и прав при откате нет: исторические команды нельзя терять. Первоначальная версия
без управления замками может работать с добавочными таблицами, но не должна менять
подтверждения броней в обход новых транзакций; до исправления доступ остаётся отключённым.

Следующий бокс: отдельный ресурс бронирования → проверка модели Tuya → назначение
проверенного device ID → права/реальное открытие/связь/резервный доступ → приёмка.
При сбое оператор проверяет бронь, устройство и command ID; `unknown` не повторяет
вслепую, помогает клиенту по согласованному порядку. Локальный выход и резервный
физический доступ проверяются с человеком на месте до допуска реальных клиентов.

Технические основания: [PostgREST config](https://docs.postgrest.org/en/stable/references/configuration.html),
[блокировки PostgreSQL](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE).
