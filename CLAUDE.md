# GarageHub — контекст проекта

Этот файл читается автоматически в начале каждой сессии. Здесь всё, что нужно знать о проекте, чтобы продолжить работу без пересказа.

## Что это

GarageHub — Telegram-бот (@garazh_rent_bot) для почасовой аренды **гаражей самообслуживания** и **детейлинг-боксов** в Москве и Московской области. Человек находит бокс, выбирает дату и часы, оставляет заявку, приезжает и сам чинит или моет машину.

Владелец проекта — Эльман (Telegram @mamedov99999, ID 5121580545). Он не программист: объясняй простым языком, давай команды для Терминала целиком и по одной, не рассчитывай на знание Linux.

## Бизнес-модель и стадия

- Сейчас стадия **набора базы**: комиссии нет, размещение для владельцев бесплатное. Цель — 20–30 объектов в Москве и области, потом рост.
- Позже: комиссия 10–15% с брони через эквайринг (ЮKassa или Т-Касса), агентская схема (ИП на УСН, агентский договор с владельцами, оферта для клиентов).
- Оплата сейчас **на месте, напрямую площадке**. Бот деньги не принимает.
- Первые 20–30 предложений владельцам (с Авито) уже отправлены, ждём ответов.

## Ключевой принцип: админ — диспетчер

На старте **все заявки клиентов идут только админу (Эльману)**, не владельцу гаража:

1. Клиент оставляет заявку и получает «заявка отправлена, ожидайте подтверждения».
2. Админу приходит уведомление: клиент, объект, дата и время, сумма + **скрытые контакты владельца** (имя, телефон, Telegram).
3. Админ сам звонит владельцу и согласует.
4. Админ жмёт «Подтвердить» → клиенту приходит «подтверждено, можно приезжать» с адресом. Или «Отказать» → бот просит причину → клиенту приходит отказ с причиной.

Позже владельцы будут подтверждать сами, поэтому архитектуру под это не ломать.

**Важно для текстов:** клиенту и владельцу **нигде не писать**, что «мы сами свяжемся с владельцем», «сами договоримся», «согласуем за вас». Это внутренняя кухня.

## Роли

- **Админы**: главный — Эльман (`ADMIN_ID`), дополнительные с теми же правами — `EXTRA_ADMIN_IDS` в `.env` (через запятую; ID человек узнаёт командой `/id` в боте; после правки — перезапуск). Уведомления о заявках, напоминания, ошибки и свежая кнопка приложения уходят **всем** админам (`service.notify_admins`); кто первым нажал «Подтвердить/Отказать» — тот и решил, у остальных кнопка ответит «уже обработана». Права админа: добавляет объекты (только он), смотрит все объекты, редактирует любое поле по одному, видит «Новые заявки» (pending, по времени начала) и «Заявки сегодня» (расписание дня, листается на 7 дней вперёд), подтверждает и отклоняет (готовые причины или своя), удаляет объекты в архив и возвращает, видит «Заявки владельцев» и «Панель» со счётчиками.
- **Клиент**: «Найти бокс» (фильтры), карусель карточек, бронирование, «Мои заявки» (предстоящие и история, отмена брони — админ получает уведомление).
- **Владелец**: кнопка «Разместить бокс» — оставляет заявку (имя, телефон, тип, адрес). Пишется в `owner_requests` (status `new` → `done`) и приходит админу с кнопкой «Обработано». Объекты владельцев добавляет админ.

## Объект (таблица `garages`)

Поля: `type` (`garage` | `detailing`), `name`, `district` (свободный текст), `address`, `photos` (TEXT[] — Telegram file_id, до 5), `price_per_hour`, `has_lift`, `has_pit`, `tool_availability` (`all` | `none` | `partial`), `box_size` (`small` до 4,5 м | `medium` до 5,5 м | `large` до 7 м), `working_hours` (текст), `description`, `owner_name`, `owner_phone`, `owner_contact`, `is_active` (false = архив), `open_hour`/`close_hour` (слоты брони, вычисляются из `working_hours`). Три поля owner_* — **только для админа, клиенту не показывать**. `owner_telegram_id` сейчас равен ADMIN_ID.

Фото хранятся как Telegram `file_id`, Supabase Storage не используется.

## Поиск (клиент)

Пошаговые фильтры, каждый можно пропустить: тип → район → подъёмник → яма → инструмент.

- **Районы** не захардкожены: список берётся из уже добавленных объектов (distinct `district`), по алфавиту, с **мультивыбором** (отметка ✓, сообщение редактируется на месте).
- **Геолокацию не использовать**: в Москве Telegram работает через VPN, геолокация ненадёжна. Это осознанное решение.
- Результаты — карусель: одно сообщение с фото и полной карточкой, ◀ N/M ▶, «Все фото», «На карте ↗» (Яндекс.Карты по адресу), «Забронировать». Объект без фото показывается с заглушкой `assets/placeholder.png`. Для детейлинга шаги подъёмник/яма/инструмент пропускаются.

## Бронирование (таблица `bookings`)

Поля: `garage_id`, `client_telegram_id`, `client_username`, `start_time`, `end_time` (timestamptz), `total_price`, `status` (`pending` | `confirmed` | `rejected` | `cancelled`), `admin_comment` (причина отказа), `created_at`, флаги напоминаний `admin_reminded`, `client_wait_notified`, `visit_reminded`.

- Даты: 7 дней вперёд, на кнопке — число свободных часов. Слоты по часу из `open_hour`–`close_hour` объекта (по умолчанию 09–22).
- Часы только подряд: нажал начало и конец — диапазон выбрался сам, сумма считается на лету. Занятые (pending + confirmed) и прошедшие недоступны. Перед записью повторная проверка занятости.
- Сообщения со слотами редактируются на месте (edit_text), а не плодятся.

## Грабли, на которые уже наступали

- **Конфликт callback_data между сценариями.** Раньше одинаковые callback (`tools_*`) ловились и добавлением, и редактированием. Теперь у каждого сценария свой класс `CallbackData` с уникальным префиксом в `tgbot/callbacks.py` (`AddCb`, `EditValCb` и т.д.). Новый сценарий = новый класс.
- Редактирование меняет **ровно одно поле**, сохраняет и показывает обновлённую карточку объекта.
- Порядок роутеров важен: `common` (меню) первым, иначе текст кнопки меню попадёт в поле ввода сценария.
- Кнопка в меню и её хендлер должны существовать парой.
- `state.clear()` не использовать напрямую — только `core.utils.reset(state)`: он сохраняет результаты поиска, чтобы карусель листалась после захода в другое меню.
- Альбом фото приходит пачкой одновременных сообщений — обработку фото и отправку брони держать под `user_lock`, иначе данные затираются.
- Колонки `open_hour/close_hour` NOT NULL: если часы не распознаны, писать значения по умолчанию 9–22, а не NULL.
- Запросы к Supabase идут из разных потоков — **HTTP/2 для клиента выключен** (core/config.py), иначе под нагрузкой случайные `ReadError`.
- Блокировка `user_lock` не реентерабельна: если обработчик уже держит её, а `service` берёт снова — зависание. Блокировку берёт только service.
- В Mini App всё, что приходит из базы, вставляется через `html\`...\`` (автоэкранирование). Не собирать HTML конкатенацией строк.
- Время из базы разбирать **только через `core.utils.parse_dt`**: Postgres отдаёт дробные секунды без нулей на конце («.17434»), а `fromisoformat` в Python 3.9 такое не понимает. Тест: `tests/t_utils.py`.
- `time.monotonic()` на маке стартует почти с нуля: не использовать 0 как «ещё не было» (из-за этого не уходили ошибки админу и не грузились фото первые секунды) — только `None`.
- Анимации экранов с `fill-mode: both` оставляют transform → `position: fixed` внутри «уезжает». Только `backwards`.
- Объекты не удаляются физически, только `is_active=false` (архив): иначе ломается история заявок.

## Telegram webhook (02.11.2026)

- Локально по умолчанию остаётся polling. Для сервера: `TELEGRAM_WEBHOOK_URL=https://домен/telegram/webhook`
  и `TELEGRAM_WEBHOOK_SECRET` (случайный секрет), сначала выполнить `sql/002_telegram_updates.sql`.
- `tgbot/webhook.py` проверяет секретный заголовок, валидирует Update, объединяет одновременные копии
  и сохраняет обработанные `(bot_id, update_id)` в Supabase через `core/db.py`. HTTP 200 — после обработки и записи.
- `api/server.py` добавляет POST `/telegram/webhook` только при наличии dispatcher и настроенного URL.
  `tools.dev_web` dispatcher не передаёт, поэтому события бота там недоступны.
- `tgbot/app.py` регистрирует webhook после запуска HTTP-сервера; при остановке оставляет его зарегистрированным.
  При возврате к polling снимает webhook без удаления ожидающих событий. SIGINT/SIGTERM корректно закрывают веб-режим.
- Один экземпляр бота: FSM и координация текущих событий в памяти. Авария между бизнес-действием и записью ID
  оставляет окно для повтора; команды будущим замкам требуют собственной идемпотентности.
- `python3 tests/t_webhook.py` — автономные тесты без реальных Telegram/Supabase; включены в `tests/run_all.py`.

Целевая архитектура webhook + Tuya, модель команд и условия запуска оборудования: `docs/SYSTEM_DESIGN.md`.
